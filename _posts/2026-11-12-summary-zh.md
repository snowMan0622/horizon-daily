### [Apache HTTP Server 曝 mod\_http2 严重 RCE 漏洞](https://www.wiz.io/blog/cve-2026-119618-rce-apache-http-server-vulnerability) ⭐️ 8.0/10

Apache HTTP Server 的 mod\_http2 模块存在一个可远程执行代码的严重漏洞，Wiz 博客将其列为关键级安全问题。社区评论指出，这似乎是自 2021 年以来该项目的首个“critical”评级漏洞，并给出了疑似对应的修复提交（apache/httpd 仓库 commit 5ed3928）。目前披露材料未提供受影响版本范围、利用条件或修复版本号等细节，实际影响需以 Apache 官方安全公告为准。

hackernews · soheilpro · 11月12日 02:11 · [社区讨论](https://news.ycombinator.com/item?id=50462177)

**「背景」** 该漏洞位于 Apache HTTP Server 的 mod\_http2 模块：HTTP/2 允许客户端在单条连接上并发发送多个请求，模块以多线程方式处理这些请求，而线程安全缺陷使一个线程可能修改属于另一线程的内存，进而造成堆破坏并可能被利用执行远程代码。据 NVD 记录，受影响版本为 Apache HTTP Server 2.4.55 至 2.4.70，GitHub 上发布的 mod\_h2 2.0.8 至 2.0.42 同样受影响。

**「运维影响」** 对暂时关闭 httpd 的运维人员，仅执行 systemctl disable --now apache2 可能不够：certbot 的 cron 任务或 systemd 定时器可能重新启动 httpd，使服务在未打补丁的情况下继续运行。在补丁可用前，需要同时停用相关自动续期任务，或确认其不会拉起 httpd。

**「社区讨论」** 有评论者认为 HTTP/2 本身是个错误，其理论收益不足以抵消增加的复杂度，且当初不应被如此快速推进；另有资深 Linux 运维表示自己十多年未接触 Apache，原以为现在主要用 nginx 等方案。这些是个人观点与经验，并非对漏洞严重性的独立验证。

### [Stela：在 x86-64 PC 上启动 Apple Silicon 的 UEFI 层](https://github.com/tylertms/Stela) ⭐️ 7.0/10

Stela 是一个 UEFI 启动程序，目标是在 x86-64 PC 上模拟 Apple Silicon 环境，包含 arm64 到 x86-64 的翻译器、面向 NVIDIA GPU 的 Metal 驱动，以及一套 Apple Silicon 硬件模型。据项目方在 v0.1.0 阶段的说明，macOS 和大多数应用能够启动，但运行缓慢且仍需大量测试。该项目目前处于早期阶段，标题中的“通用 Apple Silicon 层”容易让人误以为它是硬件方案。

hackernews · iceboundrock · 11月11日 23:02 · [社区讨论](https://news.ycombinator.com/item?id=50460154)

**「背景」** 苹果自研芯片后，macOS 主要面向 arm64 架构构建，而传统“黑苹果”依赖 x86 版 macOS 与 Intel 平台。Stela 试图在 x86-64 PC 上通过 UEFI 启动程序、arm64 到 x86-64 的翻译层、面向 NVIDIA GPU 的 Metal 驱动以及 Apple Silicon 硬件模型，直接启动未修改的 Apple Silicon 版 macOS。

**「影响与限制」** 对系统与模拟爱好者而言，这一项目展示了无需宿主操作系统、直接通过 UEFI 引导的 arm64 翻译路径，但 v0.1.0 的缓慢性能和有限测试意味着它尚不适合日常使用或依赖稳定性的场景。

**「社区讨论」** 有评论者将其理解为一种不需要宿主操作系统的模拟层，并认为这一概念很有意思；也有人指出标题应直接写明“模拟器”，因为自己起初以为这是搭载 Apple M 系列芯片的 PCIe 卡。另有评论提到 Golden Gate 仍附带 x86\_64 内核，并猜测这可能对项目有用。

### [为何编写正确软件如此困难：一篇技术长文引发讨论](https://pron.github.io/posts/correctness-and-complexity) ⭐️ 7.0/10

pron.github.io 发布了一篇题为《Why Writing Correct Software Is Hard》的长文，讨论形式正确性、复杂度理论与程序验证之间的关系。文章以忙碌海狸函数（Busy Beaver）等复杂度结果为例说明验证的固有困难，但未提供新的工具或可运行成果。Hacker News 上的讨论既肯定其概念价值，也指出技术问题：有评论者认为文章把 Rice 定理与“无法证明某个特定小程序的性质”混为一谈，并称 Rice 定理实际说的是不存在对所有程序都给出正确判定的通用方法。另有评论指出文中引用的 BB\(6\) 下界已过时，当前纪录远大于文中数值。

hackernews · AriFordsham · 11月12日 10:28 · [社区讨论](https://news.ycombinator.com/item?id=50465352)

**「背景」** 该文讨论的“正确性”问题涉及形式化验证与计算复杂性理论：形式化方法要求先有可被机器检查的规格说明，而规格本身是否“正确”往往无法由形式化工具自身判定。评论者提到的 Rice 定理则指出，不存在通用方法对任意程序判定其是否满足某个非平凡语义性质，这常被用来论证自动验证的普遍局限。

**「实际影响」** 对关注形式验证的开发者而言，这场讨论提醒两点：引用复杂度理论论证验证极限时需精确区分“不存在通用判定方法”与“某个具体程序无法证明”；引用忙碌海狸等具体数值时应核对最新纪录，否则论证的例证会显得陈旧。

**「社区讨论」** 评论者对形式正确性的适用范围存在分歧：turbobutton 认为处理真实输入和复杂人机流程的软件必然面对现实的不确定性，关键在于判断形式正确性何时值得付出成本；mpweiher 则追问“正确”本身相对于形式规约才有意义，而规约是否正确又难以界定。johnbender 具体批评文章对 Rice 定理的表述有误，kodoman 则强调让程序本身可被验证是需要深入思考的设计难题。
